# source-analysis-rule —— 源码自动定位与三层断言建立

对应主流程 Step3。**禁止要求用户提供源码路径**，须在绑定的前后端路径内自动搜索完成定位。

> 源码根路径来自 `<cwd>/.claude/auto-test/runtime.local.json`（`frontendDir`/`backendDir`）；
> glob 相对路径来自 `project.json.sourceLocate`。下文取值均为通用示例。

## 一、定位顺序

给定业务模块名（如 `order-module/list`），按下列链路自动搜索定位：

```
前端页面 → Router → API(前端) → Controller → Service → Mapper/DAO → XML/SQL → Database
```

定位方法（结合绑定 `sourceLocate`）：

| 层 | 定位方法 |
|----|---------|
| 前端页面 | Glob `<frontend>/src/views/**/<module>/**/*.vue`（或对应框架的视图目录） |
| Router | Grep 路由表中该页面路径 / 权限码 |
| API(前端) | Grep `<frontend>/src/api/**` 中页面调用的 `url` |
| Controller | 用前端 url 反查后端路由声明（`<backend>` 仓库 Grep） |
| Service | 由 Controller 注入的 Service 接口与实现 |
| Mapper/XML | 由 Service 调用的 DAO 方法 → 对应 SQL |
| Database | 由 SQL 解析涉及的表与关键字段 |

> 页面集合文件（`页面.md`）只描述业务模块；Skill 依据页面名称自动定位对应源码。

## 一点五、🔑 变体维度识别（最高优先级，覆盖完整性的核心）

> **背景（真实教训）**：某些页面看似是"一个页面"，实际同一页面会因查询到的记录**某个判别字段
> （如类型 `type` / 分类 `category`）不同**，展示**完全不同的列、表单字段、必填规则、按钮、保存接口**。
> 早期自动化只验证了"页面不白屏 + 接口可达"，**完全漏掉**了这个页面最复杂、最容易出 bug 的部分。
> 这类"由隐藏判别字段驱动的多分支渲染"是业务系统的**普遍模式**，必须在源码分析阶段主动识别。

**定位到页面后，必须先回答："这个页面会不会因某个字段的取值不同而渲染出不同的东西？"**

### 识别方法（在页面源码中 Grep 下列信号）

| 信号 | 含义 | Grep 关键词示例 |
|------|------|----------------|
| `computed` 计算列 + `if (xxx === 'a')` 分支 | 表格列随判别字段切换 | `columns = computed`、判别字段名 |
| `v-if` / `v-show` + `.includes(xxx)` | 表单项/按钮随判别字段显隐 | `v-if=`、`v-show=`、`.includes(` |
| 判别字段来源 | 判别字段是**查询后由后端返回决定**还是**用户手选** | `details[0].type`、`v-model` 绑定的顶部下拉 |
| 不同保存接口分支 | 不同取值走不同 save API | `if (...) saveA() else saveB()` |
| 次级维度 | 操作阶段 `flag`、状态 `status`、受控标志等叠加维度 | `flag`、`status`、`checkControlled` |

### 构建"变体矩阵"（必产出，作为 TestCase 与脚本的骨架）

识别出判别字段后，**枚举它的每一个取值**，为每个取值记录该页面的期望差异，形成矩阵表：

```
| 页面 | 判别字段取值 | 期望专属列/表单 | 显隐差异 | 必填/按钮/接口差异 |
```

- 判别字段取值来自源码里的**硬编码枚举分支**（逐个 `if/else if` 分支抄下来），不是猜的。
- 次级维度（flag/status/受控等）与主维度**正交叠加**，按需补充组合行。
- 矩阵的每一行 = 至少一条 TestCase + 一条参数化脚本用例。
- **覆盖目标：矩阵每一行都要有真实执行结果**。因数据/环境导致某行走不到，标 ⚠BLOCKED/Not Executed 并说明，
  **严禁**因为"其它取值已验证"就跳过某个取值当作已覆盖。

### ⚠️ 多维度必须交叉验证，不能只测各维度"独立正确"（真实教训）

**真实案例**：某页面同时存在主维度（记录类型）与次级维度（操作阶段 flag）。分别测试
"默认flag+多个类型"与"默认类型+flag切换"时表面都正常，**唯独两个维度的某个交叉点
（flag=true 且任意类型）导致页面稳定崩溃**——只测各维度"独立正确"完全没发现，因为默认测试
用例总是让其它维度停在默认值，从未真正让两个非默认维度同时生效。

**规则**：识别出多个变体维度（主维度 + 次级维度）后，**不能只各自独立取值测试**，
至少要补充若干"次级维度取非默认值 × 主维度取非默认值"的交叉组合用例（不必穷举笛卡尔积，
但至少覆盖每个次级维度在 2~3 个不同主维度取值下的表现，用于排除维度间耦合导致的缺陷）。

## 一点六、动态解析业务标识（禁止依赖静态快照单号）

> **背景（真实教训）**：把某一时刻查库得到的"真实单号"写死进用例，几天后测试环境
> 持续跑真实业务，这些单号的状态自然流转（如从"未完成"变为"已完成"），导致用例查不到明细、
> 页面回退到默认分支、被误报为失败。**静态标识在活动的测试环境里必然会过期。**

**强制规则**：变体矩阵中需要"某状态下的真实单据/编号"来驱动的用例，**执行前动态查询当前有效标识**，
不要依赖文档里写死的历史值：

- 通过"查询当前有效业务单据列表"的接口，按目标状态/类型取回**当前**有效标识，再按需要的判别字段筛选。
- 文档中的历史标识仅作**兜底候选/示例**；实测应"先动态取号，取不到再回退候选，都取不到才判 BLOCKED 并说明数据空档"。
- 有 DB 工具时优先用它查号最准；无工具时用上述列表接口查号。
- 可复用脚手架 `tests/support/resolveActionNo.ts` 的通用动态取号函数（按你的查询接口配置）。

## 二、三层断言建立

### 前端断言（UI）
- 字段校验、必填、默认值
- Loading 态、按钮禁用/启用
- 权限控制（菜单级 + 按钮级）
- 状态切换（列表状态列、流程节点状态）
- **充分性断言**（数量充足性判断类页面，见 `templates/assertion-patterns.md` 模式A）：
  剩余量 ≥ 需要量时操作必须成功、不误报"不足"。
- **中间态断言**（多步计数/状态文本类页面，模式B）：每一步都断言全部计数/状态文本，不只终态。

### API 断言（接口）
- URL、Method、Request 参数、Response 结构
- HTTP Status、业务 Code（按你的约定，如成功为 `code === 200`）
- 异常处理（非法参数 / 越权 / 重复提交）

### 数据库断言（数量守恒，核心）

重点字段（见绑定 `assertLayers.database.keyFields`），例如某业务的"可用/冻结/已用"三态数量字段。

验证：
- 更新数量是否正确
- 更新方向是否正确（增/减）
- **数量守恒**：相关数量字段之和的变化前后满足业务恒等
- 事务一致性（跨服务场景断言最终一致）

数据库读取用 DB 读工具（带精确 WHERE）；结构用 describe 工具。

## 三、断言取值时机

对每条用例记录"操作前快照 → 操作 → 操作后快照"，仅输出**关键字段的变化**（见
`rules/execute-rule.md` 证据收集与 Token 控制）。
