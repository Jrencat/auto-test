# testcase-rule —— TestCase 增量维护规范

对应主流程 Step4 / Step5 / Step9。

> 脚本/用例目录来自绑定 `project.json`（`testcaseDir`、`scriptDir`）。下文取值均为通用示例。

## 一、存放位置

```
docs/testcases/<module>/
├── E2E_业务主流程用例.md
├── API_接口测试用例.md
└── IMPORT_专项测试用例.md
```

- `<module>` 用业务模块标识（如 `order-module`）。
- 首次执行自动创建；模板见 `templates/testcase-e2e.md` / `testcase-api.md` / `testcase-import.md`。

## 二、增量维护原则（严禁整体覆盖）

- **保留**：用例 ID、状态、历史执行记录。
- **新增**：追加到文件末尾或对应分组。
- **修改**：仅局部更新变化字段。
- **废弃**：标记 🚫DEPRECATED，不物理删除。

## 三、用例 ID 规范

`<MODULE>-<TYPE>-<NNN>`，例如：
- `ORDER-E2E-001`（端到端主流程）
- `ORDER-API-013`（接口）
- `ORDER-IMPORT-004`（导入专项）

ID 一经分配不得复用/重排。

## 四、状态字段（终态只允许真实结果）

| 状态 | 含义 |
|------|------|
| ✅ PASS | 真实执行通过 |
| ❌ FAIL | 真实执行失败（须附失败归因与疑似源码位置） |
| ⚠ BLOCKED | 输入/环境/权限缺失，无法执行 |
| 🚫 DEPRECATED | 已废弃 |

严禁以 🟡待执行 作为执行完成后的终态。

## 五、回写（Step9）

执行后按运行结果回写每条用例的：状态、最近执行时间、执行命令引用、
证据路径（截图/日志片段/数据库字段变化）、失败归因（如有）。

## 六、覆盖要求

- E2E 覆盖业务流转全链路与正向/逆向/并发/幂等/重复提交/超量/非法参数。
- IMPORT 覆盖导入入口：空文件/类型错误/超限/表头错误/特殊字符/重复数据/部分成功/全部失败。
- 每条 E2E/IMPORT 用例必须有对应自动化脚本（见 `rules/script-rule.md`）。
- **变体矩阵覆盖（强制）**：对 `rules/source-analysis-rule.md` §1.5 识别出的每个多分支页面，
  其变体矩阵的**每一行取值都要有对应用例**（VARIANT 类型，见下）。默认追求**全取值覆盖**，
  而非抽样——抽样只在明确的数据空档/时间受限下允许，且必须在报告里列明未覆盖的取值。
- **断言模式库覆盖（强制，源自真实客户问题）**：见 §八点五。

## 七、VARIANT 变体矩阵用例（多分支页面专用，客户交付必备）

多分支页面（同一页面因判别字段不同渲染不同列/表单/按钮/接口）用独立的
`VARIANT_数据变体矩阵用例.md` 记录，或在 E2E 文件内以矩阵表承载。ID 用 `<模块>-<页面缩写>-NNN`。

矩阵用例表**每行至少含**：判别字段取值、驱动用的真实标识（动态取号）、期望专属列/表单、
显隐/必填/按钮/接口差异、真实渲染结果（执行后回填）、状态、证据。

## 八、数据变体默认检查清单（强制，每条可输入用例都要考虑）

> 不得只用文档给的"正常数据"。每条涉及输入的用例，都要主动设计多组数据变体。
> 会真实写库的变体，用**不存在的标识**触发校验分支，或用 `<dataIsolationPrefix>`（默认 `TEST_AUTO_*`）隔离，
> 避免污染真实数据（见 `rules/environment-rule.md`）；无 DB 回滚工具时尤其如此。

| 类别 | 变体取值（至少覆盖） |
|------|--------------------|
| 基础 | 正常值 / 最大值 / 最小值 / 边界值 / 超长字符串 / 空字符串 / Null / Undefined |
| 特殊输入 | 特殊字符 / Emoji / HTML特殊字符 / SQL特殊字符 / XSS字符 / 多语言字符 / 特殊编码字符 |
| 数值异常 | 极大值 / 极小值 / 负数 / 小数精度边界 / 超出业务上限 |
| 数据状态 | 重复数据 / 已存在数据 / 不存在数据 |
| 权限场景 | 不同权限账号 / 权限不足 / 未登录 / 无效token |
| 用户行为 | 连续点击 / 重复提交 / 并发提交 / 快速操作 / 页面刷新 / 返回 |
| 异常场景 | 网络异常 / 接口异常 / 超时 / 服务异常（可模拟时） |
| 文件场景（如适用） | 空文件 / 非法格式 / 超大文件 / 格式错误 / 内容异常 |

**断言维度不止业务结果**：还要观测 Console Error / Promise Rejection / JS Runtime Error /
Network Error / HTTP 异常 / Loading 是否正常结束 / Toast 是否正确 / 白屏 / 崩溃 / 卡死 /
异常刷新 / 前后端数据一致性 / 明显性能问题（见 `rules/execute-rule.md` 证据收集）。

## 八点五、通用断言模式库（强制引用 `templates/assertion-patterns.md`，源自真实客户问题）

数据变体覆盖"输入的多样性"，但客户反复反馈的一类 bug 是**不报错、但期望值≠实际值**的断言型缺陷。
对匹配的页面**必须**套用 `templates/assertion-patterns.md` 的模式，作为独立用例：

- **模式A｜数量充足性精确断言**（适用：使用/扣减/出库等按剩余量判断可否操作的页面）：
  预置已知数量 → 使用量 ≤ 剩余量 → 断言**操作成功**且**无"不足"类提示** + 数据库关键数量字段精确变化且守恒。
  数据变体：剩余=需要（边界）、剩余>需要、剩余<需要（反向应真失败）、单位/规格换算、
  多批次合并、被冻结部分是否计入可用、小数精度。**防"数量充足却误报不足"。**
- **模式B｜多步中间态逐步断言**（适用：扫码接收、逐项汇总、随操作累积的计数/状态徽标页面）：
  把操作编码为有序步骤序列，**每一步**都断言全部相关计数/状态文本（总数、当前分组数等），
  不只看终态。覆盖：分组切换、切回已处理分组、重复操作同一项、跨分组归属、撤销/清空。
  **防"多步操作后计数/状态显示错乱"。**

## 九、Fail 分类（回写与报告都要用，禁止一律归为产品Bug）

每个 FAIL/BLOCKED 必须归入其一：**产品缺陷 / 自动化脚本问题 / 环境问题 / 配置问题 /
第三方依赖问题 / 网络问题 / 测试数据问题**。产品缺陷候选须标注严重程度
（Blocker/Critical/Major/Minor）与【疑似原因】+ 仍需排查项（证据不足时不得编造根因）。

### 🔴 归类为"测试数据问题"前必须先用 API 核实（强制，真实教训）

**背景**：曾把"某页面查询后表头未按预期切换"直接归因为"标识已失效/测试数据陈旧"，
未经核实就写入报告。后续深入排查证明该标识**完全有效**（直接调用查询接口，数据真实存在、
判别字段正确），真实原因是一个与判别字段无关的前端渲染崩溃缺陷——即"测试数据陈旧"
的结论是**凭直觉猜的，没有核实就写进了交付报告**，属于严重的方法论错误。

**强制规则**：变体用例出现"实际渲染/返回与预期不符"时，在写下"测试数据陈旧/标识已失效"之类结论前，
必须先：
1. 直接对涉及的查询接口发起真实调用，核实数据是否真的不存在或状态是否真的不符合预期；
2. 若数据接口层面完全正常（返回了预期数据），**不得**再往"数据问题"方向归因，应转为怀疑前端/脚本问题，
   进一步抓取浏览器 `pageerror`/`console.error` 事件、请求响应时序，定位真实渲染链路；
3. 怀疑某维度导致问题时，**用另一个正交维度的对照数据交叉验证**，排除偶然性、精确定位问题维度，
   而不是猜一个维度就下结论。

**同类经验**：见 `rules/environment-rule.md §并发执行安全` 中"未隔离重跑先别下结论"的姊妹规则——
两者都是"先用最小代价的核实手段排除简单解释，再下结论"的同一纪律。
